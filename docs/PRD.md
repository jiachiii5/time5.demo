# PRD 文件：社交合作功能 (多人共編、權限管理)

## 1. 專案概述
- **背景與動機**：在現代專案管理與協作中，多位成員經常需要同時編輯或檢視同一份文件、專案計畫或任務清單。為了避免資料衝突並確保機密資訊不被越權存取，我們需要一個穩定的多人共編與權限管理機制。
- **目標用戶**：需要團隊合作的專案經理、開發人員、內容創作者以及一般企業員工。
- **核心價值主張**：提供即時或非同步的協作體驗，結合細緻的權限管控（如擁有者、編輯者、檢視者），讓團隊合作更安全、更有效率。

## 2. 功能需求

### 權限管理 (Permission Management)
1. **作為** 專案擁有者 (Owner)，**我希望** 能夠邀請其他使用者加入專案，**以便** 讓他們參與協作。
2. **作為** 專案擁有者 (Owner)，**我希望** 能設定個別成員的權限角色（編輯者、檢視者），**以便** 控管他們對專案內容的修改權利。
3. **作為** 系統，**我希望** 能在每次使用者嘗試修改內容時驗證其權限，**以便** 防止未經授權的修改。

### 多人共編 (Multi-user Co-editing)
4. **作為** 編輯者 (Editor)，**我希望** 能夠編輯專案內的共享文件或任務，**以便** 貢獻我的工作成果。
5. **作為** 團隊成員，**我希望** 能夠看到其他正在檢視或編輯同一份文件的人員清單，**以便** 知道目前有誰在線上。
6. **作為** 編輯者 (Editor)，**我希望** 系統能夠處理同時編輯時的衝突（例如文件鎖定或最後寫入獲勝），**以便** 確保資料一致性。

## 3. 非功能需求
- **技術限制**：基於 Flask + Jinja2 + SQLite 架構進行開發。由於 SQLite 對於高併發寫入支援有限，多人「即時」共編需採用悲觀鎖定 (Pessimistic Locking，如編輯時鎖定文件) 或基於 API 的最後修改時間檢查 (Optimistic Locking) 以防止資料覆寫。
- **效能考量**：在多人同時存取同一專案時，API 的回應時間應維持在可接受範圍（< 500ms）。
- **安全考量**：所有修改資料的請求 (POST/PUT/DELETE) 都必須嚴格檢查使用者的 Session 與專案角色權限 (RBAC)。防止越權漏洞 (IDOR)。

## 4. MVP 範圍

**Must Have (必須擁有)**:
- 專案與文件的建立。
- 基本角色權限系統（Owner, Editor, Viewer）。
- 邀請成員加入專案並指派角色。
- 權限驗證：只有 Owner/Editor 可以修改文件，Viewer 只能閱讀。
- 衝突預防：基本的最後修改時間檢查 (Optimistic Locking) 或編輯鎖定機制。

**Should Have (應該擁有)**:
- 顯示專案內目前的成員名單與角色。
- 編輯鎖定：當某人進入編輯模式時，其他人只能檢視直到對方釋放鎖定。

**Nice to Have (加分項目)**:
- 即時看到其他使用者正在線上的狀態 (WebSockets/Polling)。
- 詳細的編輯歷史紀錄與還原功能。
